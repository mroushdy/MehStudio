# Existing coupled spatial solvers: integration audit

Recommend a **separate, pinned BEAT Engine worker** for the next full spatial stage, with MEH Studio producing its documented compiled-system requests and retaining the resulting complex source basis. Boundary Lab supplies a relevant authoring/compiler example and a useful comparison application. Reimplementing a complete FEM–BEM solver in the offline HTML is not the justified next step.

This was a bounded source/documentation audit on 2026-09-29. Neither solver was installed or executed, no Julia dependencies were prepared, and no GPL solver code was copied into MEH Studio. The Python checked in this task could not find `beat_engine`; `julia` was not found on its PATH. That is a scoped environment observation, not proof that no other installation exists.

## Worker and request contract

The public Python entry points are `EngineWorker`, `WorkerPool`, `EnginePaths`, and `engine_paths`. A client resolves the selected backend paths, supplies the Julia executable/project/solver script/thread count, starts the worker, checks `worker_info`, and consumes `submit(...)` events to completion or explicitly closes the iterator. The worker source accepts a local request path or a mapping. Version 0.3.0 advertises file and inline-JSON transports, protocol v1, request/compiled-system v1, result v2, field-array v1, and mesh-data v1. It also advertises the two phasor conventions and optional interface-average velocity/radiated-pressure quantities. Capabilities must be checked at startup rather than inferred from a package version. [Public exports](https://github.com/JWSound/BEAT_Engine/blob/e6b3037df04d3ac32d2bd4586d2e9f0312e2d91f/src/beat_engine/__init__.py), [worker transport](https://github.com/JWSound/BEAT_Engine/blob/e6b3037df04d3ac32d2bd4586d2e9f0312e2d91f/src/beat_engine/worker.py), [v0.3.0 announcement](https://github.com/JWSound/BEAT_Engine/blob/e6b3037df04d3ac32d2bd4586d2e9f0312e2d91f/src/beat_engine/beat_contract/worker-v1.json).

Requests carry resolved meshes, regions, boundary groups, interfaces, components, excitation ports, frequencies, requested outputs and solver options. Geometry uses metres after scale/translation. Interface maps use original-mesh zero-based vertex/face indices and explicit normal signs. Select `exp(+i omega t)` explicitly; an omitted option retains a legacy convention. Complex responses remain separate ordered excitation columns. Voltage basis amplitude follows `transducer_reference_voltage_v`, so do not assume 1 V. Result v2 contains typed, shaped, little-endian complex arrays. Mixing, crossovers and display normalization stay with the client. Use worker-local absolute mesh paths for the first integration. [Pinned compiled-system contract](https://github.com/JWSound/BEAT_Engine/blob/e6b3037df04d3ac32d2bd4586d2e9f0312e2d91f/docs/BEAT%20Compiled%20System%20Contract.md).

## Coupling and motor fit to our model

The coupled model joins bounded FEM air and a single unbounded BEM region in one solution, enforcing interface pressure/flux continuity. Motors use `Re`, `Le`, `Bl`, **dry `Mmd`**, `Cms`, `Rms`, and a motion axis. Pressure force and normal velocity use the same surface projection; one motor can connect separately meshed front and rear surfaces. Consequently, catalog `Mms` and scalar `Sd` must not simply be pasted into unrelated mesh surfaces. The optional lumped sealed rear compliance must not duplicate an already meshed rear chamber. First-order FEM tetrahedra and matching BEM interface triangles need conforming maps, not only coincident CAD surfaces. Bulk damping does not replace thermoviscous gap losses. [Coupled formulation and requirements](https://github.com/JWSound/boundary-lab/blob/bb9030c4ae0b5906569b3b3932e221a0c97670ac/docs/Coupled%20Solver.md), [current engine motor structure and impedance](https://github.com/JWSound/BEAT_Engine/blob/e6b3037df04d3ac32d2bd4586d2e9f0312e2d91f/src/beat_engine/julia_local/src/BeatEngineCoupled.jl).

There is a real multi-region project, not just a feature claim: `Multi_region_SAWMOD.blab.json` references throat FEM, side-slot FEM, sealed-volume FEM, and a conformed exterior BEM mesh. Its LF motor attaches to moving faces in both the side-slot and sealed-volume regions; separate HF/MF/LF voltage ports and four FEM–BEM interfaces are present. Mesh scale is 0.001, and the sample uses symmetry completion/orbit fields. This demonstrates the authoring topology. Its motor values, losses, filters and delays are example-specific, and are not inputs for this user’s horn. [Pinned example](https://github.com/JWSound/boundary-lab/blob/bb9030c4ae0b5906569b3b3932e221a0c97670ac/examples/Multi_region_SAWMOD/Multi_region_SAWMOD.blab.json).

Our existing `spatial-motor-network.cjs` accepts a **unit projected-volume-flow acoustic impedance matrix and matching observer transfer**, with motors and sealed rear compliance coupled locally. BEAT's fully coupled voltage responses cannot be inserted into that contract directly. A first integration should import those voltage response columns through a separate qualified-results adapter and avoid applying motors, rear compliance or radiation a second time. Reusing the existing impedance adapter instead requires prescribed-flow front/horn/exterior solves that exclude the rear chamber and motors, plus an explicit extraction of the power-conjugate pressure matrix and observer transfer. That extraction has not been implemented or demonstrated.

## Concrete next integration

The following is our proposed adapter/qualification sequence, not work already performed:

1. **Pin a compatible baseline.** First reproduce the Boundary Lab example using its v0.2.0 engine pin in an isolated environment. Evaluate v0.3.0 separately before adopting new transport/mesh features. Capture actual worker announcement, engine revision, runtime, backend and precision with every result.
2. **Compile the exporter manifest.** Carry the design hash, SI coordinates, source IDs, projected areas, outward normals, air-domain and surface tags into the compiled graph. Add a derived-mesh hash and reject stale maps after any remesh. Retain physical source identity independently of tag numbering.
3. **Use the actual four entries.** A straightforward faithful topology is one connected FEM air volume covering all front chambers, ports and horn, a shared rear FEM air volume containing all four rear diaphragm faces, and one surrounding BEM exterior joined at the horn mouth. Connect each front/rear pair to one motor. This represents the saved shared 108 L cavity without replacing it with four independent compliances. Preserve any actual rear outlet topology if the design later enables one.
4. **Qualify source normalization.** Start with a plane-piston/duct case and prescribed unit volume flow. BEAT’s source is normal velocity, so map volume flow using the integrated source projection. Then qualify a single explicit-Mmd motor at the chosen reference voltage; verify RMS versus peak conversion using power balance and excursion. Scale the resulting voltage basis to the saved 1 V RMS per mid only after that check.
5. **Keep all response columns.** Initially solve the full geometry with symmetry off. Request exterior complex pressure at explicit metre-based observation points, per-driver velocity/current, and interface diagnostics. Retain muted-driver passive loading. Test equal-phase, one-driver-only and opposing-phase drives before considering symmetry reductions. Do not add an uncharacterized HF driver or imply a measured crossover.
6. **Reuse our acceptance machinery.** Run the existing analytic/Hornresp fixtures where topologies overlap, then refine spatial meshes at selected frequencies across the tuning band. Check complex pressure, self/mutual loading, interface flux, energy, excursion and port speed. Establish actual runtime/memory on this horn before promising broadband sweeps. Import only qualified samples into offline MEH Studio; distinguish them from interpolation and fast axial predictions.

## Evidence limits

### Importer tolerances and backend qualification

The prototype's full-spatial importer has strict defensive gates verified with synthetic operators. They are **not calibrated BEAT/FEM–BEM accuracy thresholds**. Reciprocity uses the largest entry of `Z - transpose(Z)`, limited to `1e-8 * max(1, max(abs(Z)))`. Passivity uses the smallest eigenvalue of the full complex Hermitian matrix `H = (Z + conjugateTranspose(Z))/2`, limited below by `-1e-9 * max(1, max(abs(H)))`. These SI-scale floors and maximum-entry normalizations must be recorded when comparing diagnostics produced with another norm. The raw impedance matrix is not symmetrized or modified for the solve.

The initial full-spatial adapter used only the symmetric real part for its passivity diagnostic. A regression exposed a false acceptance when small imaginary nonreciprocity sat on a large reactive diagonal: diagonal `0.001 + j*1e6`, off-diagonal `Z01 = j*0.004`, `Z10 = -j*0.004`. The reciprocal gate passes, but the true Hermitian minimum is `-0.003`, and a quadrature excitation extracts negative real power. The corrected diagnostic includes that imaginary antisymmetric term. The local native FEM already used the full Hermitian matrix, and the delivered fast-model/local-front curves are unaffected.

A future backend policy should be versioned and justified before adopting changed tolerances:

- Preserve raw reciprocity metrics, full-Hermitian eigenvalues and worst-mode vectors, scales, conventions, residuals and provenance. Keep rejected or unresolved samples visibly experimental.
- Separate fixed-mesh solver/precision/quadrature error from mesh, interface and exterior discretization error. Compare both the source operator and observer transfers under refinement, including frequencies around sharp features.
- Use a documented dissipation/power error budget for negative Hermitian eigenvalues; a large reactive impedance is not evidence that negative dissipation is harmless. Mesh differences estimate uncertainty and do not by themselves establish a rigorous error bound or prove passivity.
- Verify source power against exterior radiation plus modeled losses, including the worst Hermitian eigenvector excitation. Near-zero unresolved modes remain marginal. Do not repair matrices by silently symmetrizing them or clipping eigenvalues.

The released strict gates stay in force. Admitting a dataset under a future policy requires explicit numerical evidence and a separately reviewed importer revision; this source audit does not authorize an automatic tolerance increase.

The upstream numerical reference documentation includes manufactured exterior fields, cavity modes, independent excitation superposition, symmetry, coupled continuity/replay, condensed-versus-monolithic motor solves, and precision comparisons. It states that shared assembly kernels limit independence of some comparisons, and that accelerator qualification is hardware-specific. These are inspected upstream tests and claims, **not tests run in this task**, and not measured validation of the current horn. [Pinned numerical reference coverage](https://github.com/JWSound/BEAT_Engine/blob/e6b3037df04d3ac32d2bd4586d2e9f0312e2d91f/src/beat_engine/julia_local/tests/README.md).

The selected route avoids a second full-solver implementation and addresses the missing coupled horn/exterior physics directly. Remaining work is substantial but concrete: acquire/qualify the runtime, compile conforming mesh/interface maps, audit driver normalization and dry mass, run the actual four-port model, and demonstrate mesh convergence and measurement agreement. No performance, GPU availability, complete current-design solve, or physical-accuracy claim follows from this source inspection.
